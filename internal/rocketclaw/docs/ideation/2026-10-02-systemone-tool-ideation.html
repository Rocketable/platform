Grounding Context

Codebase Context

Decisions already made with the user

  • systemone is a command inside execute, like read, apply_patch, grep and glob. The model reaches it through Starlark code, not as a top-level function call. (Settled in review; the first draft of this report missed it.)
  • TypeSafe's wire format is the standard: state plus Noul, Choice and Score questions. Other vendors adapt to it, so the feature is named after the concept, not the vendor.
  • Jev's weak spots are a known, accepted risk: injection, numbers, very literal reading, broad questions and large state. Ideas may reduce them but don't treat them as blockers.
  • The support is our own and native. No MCP server, no reuse of webfetch/bash/curl, no vendor SDK.
  • Decisions RocketClaw makes itself are a later phase and must not widen the first version. That covers the permission reviewer, guardrails, background "show the human?" and skill suggestion.

What the code says

  • System One can't be a model provider. The agent loop only speaks the OpenAI Responses API, and ModelResolver.Resolve returns an *openai.Client. A model that only returns probabilities fits as a command.
  • Inside execute, commands are flexible.
    • Keyword arguments are Starlark values. They are converted to JSON and checked by a full JSON Schema validator (codemode.go:240-325), not by OpenAI's strict mode.
    • functionTool only sets top-level required and additionalProperties (tools.go:630-651), and codeModeHostRequiredFields picks the truly required fields per command (mcp_tools.go:849-866). Nested schemas can therefore use keys the caller chooses, and oneOf.
    • A command can return a real Starlark value through CallValue, as bash does (codemode.go:210-226, mcp_tools.go:779-791).
  • Fan-out is built in. map(items, fn, concurrency=16), gather, race and race_first run calls in parallel: 16 by default, at most 64 (codemode/fanout.go:15-20, 67-70).
  • Where built-ins reach.
    • Built-ins like read/grep are execute-only (CodeModeOnlyHostTool, tools.go:94-101).
    • Every nested call goes through the same allow/deny/auto gate (permission_gate.go).
    • Workflow workers get all runtime tools (raw_run.go:86-89). Handoff deliberately gets none (handoff.go:45).
  • Configuration. providers.<name> holds {api_key, api_base_url}, and models are written as provider/model. Any config string can be an AWS Secrets Manager reference. Secrets must stay out of error messages and the web config view.
  • Permissions. Rules default to deny. auto rules go to a 90-second child-agent reviewer that fails closed. The rc005 lint rule only checks websearch/webfetch combined with write access.
  • Line budgets. internal/rocketclaw (with cmd/rocketclaw) has 22,350 lines; internal/rocketcode has 10,500.

Prior art

  • OpenCode V2 (experimental). It has a provider-neutral "Evaluation" layer whose System One route targets <base>/systemone. TypeSafe, OpenRouter and OpenCode Zen all serve that format. It also includes a recorded real Jev 1.13 response. It is not yet exposed to agents.
  • Community MCP servers. At least four expose Jev to coding agents. Lessons from them:
    • Thresholds live in code.
    • Files are read server-side, so agents never paste text.
    • Model versions are pinned.
    • The tool never emits "allow".
    • "A check an agent can decline to call is not a check", so mandatory checks belong in the harness.
  • Injection research.
    • Check Point broke a Jev-based app; labelling the document "untrusted" didn't help.
    • An independent NTU study found 0.2% high-confidence hijacks over a closed 3-action set, and showed that returning probabilities to the attacker helps the attack.
    • jev-sec-bench found Jev slightly under-confident (ECE 0.059).

Ranked Ideas

How the survivors fit together. Ideas 1–5 form one coherent first version:

  1. Reuse the provider config and HTTP client RocketClaw already has.
  2. Make systemone(...) take TypeSafe's request exactly as documented.

  4. Return the typed answer as a Starlark value, so the script owns the thresholds.
  5. Treat the risk as data leaving the host.

1. Reuse the existing provider config and HTTP client

  • Idea 1
  • Wiring and placement
  • Confidence 85%
  • Complexity Low

Description

Don't write a new HTTP client, credential type or config section. The operator adds a normal provider entry, providers.typesafe = {api_key, api_base_url: "https://api.typesafe.ai/v1"}, and one setting, systemone_model: "typesafe/jev-1.13.0", shaped like auto_approver_model. The command resolves that string through the existing model resolver. It then calls the general-purpose client.Post(ctx, "systemone", req, &resp) on the *openai.Client it gets back. Base URL, bearer key, AWS secret references, provider-error logging and retries all come for free.

Switching to OpenRouter (openrouter/typesafe/jev-1.13) or OpenCode Zen is a config edit. The version pin lives in the model string, so threshold tuning isn't silently invalidated when jev-latest moves.

Wiring and placement
Basis
direct:
  • openai-go v3 client.go:195: func (r *Client) Post(ctx context.Context, path string, params any, res any, opts ...option.RequestOption) error.
  • requestconfig.go:285: MaxRetries: 2. It retries 408/409/429/5xx and honors Retry-After/Retry-After-Ms, which matches TypeSafe's own SDK policy.
  • WithBaseURL adds the trailing slash, so …/v1/ + systemone joins correctly.
  • model_resolver.go:84-91 sets the key and base URL. model_resolver.go:48 splits provider/model on the first slash only.
external: OpenRouter and OpenCode Zen serve /systemone (OpenCode V2 recorded fixtures). All five ideation agents proposed this independently.
Rationale
It answers "configurable endpoint or TypeSafe only?" with a config entry instead of a feature. It reuses the secret handling that is already tested: no secret in errors, and none in the web config view. Almost no lines go against the budget.
Downsides
  • OpenAIConfig fields such as rocketcode_auth and autocompaction_threshold mean nothing here.
  • A provider with rocketcode_auth: chatgpt takes a different client path (model_resolver.go:75-82), so config validation must reject it for this setting.
  • There is no default request timeout beyond the context, so the call needs a cap; TypeSafe's SDK uses 30 s.
  • Vendor error bodies come back verbatim in apierror.Error(), so don't pass them straight into the script.
  • The new setting needs normalization, docs and tests, like auto_approver_model.
  • The rocketcode resolver interface hands out an *openai.Client, so the built-in can call Post without new plumbing.

2. systemone(...) takes TypeSafe's request exactly as documented

  • Idea 2
  • Call contract
  • Confidence 85%
  • Complexity Low

Description

Because the command lives inside execute, there's no strict-schema problem to work around. The command takes two keyword arguments:

  • state: a string, dict or list
  • questions: a dict keyed by names the agent chooses, each a Noul, Choice or Score exactly as in TypeSafe's API reference

Structured instructions and criteria objects work too, including data fields referenced in backticks such as `spec`. The command doesn't take a model argument; the operator's systemone_model (idea 1) decides.

Its execute schema is a real JSON Schema:

  • questions uses additionalProperties with a oneOf over the three types.
  • The 255-option and 10-level limits are written into the schema.
  • Only state and questions are required.

Mistakes are caught by the validator execute already runs, before any HTTP call.

def main():
    r = systemone(
        state={"diff": read(filePath="changes.diff"),
               "spec": read(filePath="docs/billing-spec.md")},
        questions={
            "touches_billing": {"type": "noul",
                "instructions": "Does `diff` change how invoices are charged?"},
            "spec_verdict": {"type": "choice",
                "instructions": "Does `spec` support the change in `diff`?",
                "criteria": {"supports": None, "contradicts": None, "says_nothing": None}},
        },
    )
    a = r["answers"]
    if a["touches_billing"]["noul"] < 0.5:
        return "no billing impact"
    return "billing change; spec " + a["spec_verdict"]["choice"]
Axis
Call contract
Basis
direct:
  • codemode.go:246-253: keyword arguments go through kwargsToMap, then validateArgs(schema, callArgs). That is a full JSON Schema validation (schema.Resolve(nil) … resolved.Validate(instance), lines 295-325).
  • tools.go:630-651: functionTool only sets top-level required/additionalProperties.
  • mcp_tools.go:849-866: codeModeHostRequiredFields picks the required fields per command (for example glob, grep → pattern).
external: the TypeSafe API reference (question shapes, 255/10 limits, structured instructions with backtick references).
Rationale
It keeps TypeSafe's format as the standard with no translation layer and no lost features. The agent can follow TypeSafe's own docs and examples word for word, and agent-written code can build questions in loops (one Noul per file, per option, per argument).
Downsides
  • The agent has to write good questions. Broad questions are Jev's worst case; see idea 6 for a fix.
  • The oneOf schema adds about a screenful of schema code, and its validation errors are less friendly than a hand-written message.
  • No "none of these" option is added automatically. The agent has to include one when abstention matters, and the description should say so.

3. Execute-only built-in next to read/grep; the script builds the state

  • Idea 3
  • Wiring and placement
  • Confidence 80%
  • Complexity Medium

Description

Make systemone a rocketcode built-in, add it to CodeModeOnlyHostTool next to read, apply_patch, grep and glob, and configure it through one Config.SystemOneModel field resolved by the model resolver every loop already holds. When the field is unset, an explicit inert command takes its place and the agent doesn't see it.

Three things then come for free:

  • State without copy-paste. The script builds state from read(...), grep(...) and spill files. File contents never pass through the model's output tokens, and read's own permission rules (including the .env protection) already decide what can be read.
  • Fan-out. map(paths, fn, concurrency=16) judges many items in parallel (up to 64), so there's no need for a batch API.
  • Reach. Root agents, task subagents and workflow workers all get it. Handoff stays tool-free on purpose.
def main():
    out = glob(pattern="docs/runbooks/*.md")
    if out == "No files found":
        return out
    paths = out.splitlines()
    q = {"fits": {"type": "noul",
                  "instructions": "Does this runbook cover a failed payout?"}}
    rs = map(paths, lambda p: systemone(state=read(filePath=p), questions=q), concurrency=16)
    hits = [paths[i] for i in range(len(paths)) if rs[i]["answers"]["fits"]["noul"] >= 0.8]
    return "\n".join(hits)
Axis
Wiring and placement
Basis
direct:
  • tools.go:94-101: CodeModeOnlyHostTool lists read, apply_patch, glob, grep, webfetch, bash.
  • fanout.go:67-70: gather, map, race, race_first.
  • fanout.go:17-19: DefaultConcurrency = 16, MaxConcurrency = 64.
  • tools.go:207-219: read uses sfs.readPermissionSubject.
  • raw_run.go:86-89: workflow workers get all runtime tools.
  • handoff.go:45: RestrictTools([]string{}).
external: jevwire reads files server-side so agents never paste text. Its author measured 38 files, about 108k input tokens, $0.0045, under 1 s.
Rationale
It matches how you described the feature. It also settles several open questions in one move: built-in or custom tool, whether workflows get it, how state avoids copy-paste, and how to judge many items. Nothing new is needed for any of them.
Downsides
  • The code lands in the smaller budget (rocketcode, 10,500 lines) and in the general-purpose loop package.
  • It adds a field to rocketcode.Config.
  • With map, every nested call is still permission-checked. If an agent's rule for systemone is auto, each branch could wait for the 90-second reviewer, so in practice the rule should be allow or deny.
  • The 32k state limit needs a clear error.
  • read returns text formatted for the model, not raw content: <path>/<content> tags, a 1: prefix on every line, and an end-of-file note (filesystem.go:135-150). State built from it carries that formatting, and Jev handles numbers poorly. Brainstorming should decide between three options: accept it, strip it in the script, or give scripts a way to get raw text.

4. Return a typed Starlark value; the script owns the thresholds

  • Idea 4
  • Call contract
  • Confidence 75%
  • Complexity Low

Description

Give the command a CallValue, the way bash returns a struct. The result is TypeSafe's response as Starlark values: r["answers"][id] with noul, choice, probabilities, confidence, score and legend, plus model and usage. Probabilities stay inside the script; the model only sees what main() returns.

This covers what the first draft tried to do with a Go-side band table. The comparisons Jev's docs say belong in code now happen in the agent's code. There's no extra threshold machinery in Go, and context stays small because the script can return one line per decision.

Axis
Call contract
Basis
direct:
  • codemode.go:210-214: if tool.CallValue != nil { return tool.CallValue(ctx, args) }.
  • mcp_tools.go:779-791: bash returns a struct through result.Data.
  • attachments.go:58-63: Data is meant for code-mode bindings.
  • Only execute's final output is clipped and spilled, so returning a compact string is the script's job.
external: jevwire says "thresholds, gating, arithmetic in code". TypeSafe's how-to-build guide routes on confidence in code.
Rationale
It gives the agent the full answer to compute with, and keeps the model's context small. It is also the natural partner to idea 2: TypeSafe's format goes in, TypeSafe's format comes out.
Downsides
  • The thresholds are whatever the agent writes, not reviewed constants; see idea 6.
  • Today the Data→Starlark path is special-cased for bash. A built-in can set its own CallValue, but the shared path may need a small change.
  • A prompt-injected state can still sway a single answer. The agent's code should combine several narrow questions rather than trust one.

5. Treat it as data leaving the host: own permission bucket, deny by default

  • Idea 5
  • Trust and safety
  • Confidence 75%
  • Complexity Low

Description

Unlike webfetch, System One can't bring attacker-written text back. Its answers are labels drawn from options the agent wrote, plus numbers. The operator fixes the destination in config, not the agent. So the real risk only goes outward: workspace data sent to a third party.

That gives a short policy:

  • A dedicated systemone permission bucket.
  • Off the default-allowed list, so access is deny-by-default and granted with one explicit line per agent.
  • What can be read is still governed by read's own rules, because the script reads through read.
  • No change to the rc005 lint, which guards against untrusted content flowing in.
Axis
Trust and safety
Basis
direct:
  • agentlint.go:305 triggers only when websearch or webfetch is allowed together with write access ("can write external content to …").
  • guardian.go:64/70: third-party destinations are not pre-approved, and sending workspace data outside is "high or critical" risk.
  • permission_gate.go:31-62: nested execute calls are re-checked.
  • The workflow-bucket plan set the precedent that new capabilities get their own bucket.
reasoned: with at most 255 options, each answer carries at most 8 bits, all chosen from agent-written text.
Rationale
It settles "default-allowed or explicit, and does the lint change?" with a stated argument rather than copying webfetch's risk profile out of habit. It adds no lint code.
Downsides
  • The "labels only" argument breaks if the agent builds options from untrusted state, for example scraped page titles.
  • Operators have one more bucket to learn.
  • An auto rule would put the 90-second reviewer in front of every call inside a fan-out.
  • Allowing it by default was considered and rejected, because it conflicts with the guardian's stance on third-party destinations.

6. Human-written named checks (follow-up fork)

  • Idea 6
  • What agents use it for
  • Confidence 50%
  • Complexity Medium

Description

For decisions that repeat, such as "is this destructive?", "which skill?" or "does this evidence support the claim?", keep reviewed question sets and thresholds in workspace files. A script could then call something like systemone(check="supports-claim", state=...) instead of writing the questions itself. Free-form questions stay the default. Checks are an optional, reviewed layer on top.

Axis
What agents use it for
Basis
direct: dynamic_workflow_tool.go:88-107 lists allowed names through VisibilitySubjects and uses the name as the permission subject. That precedent fits checks too. external: TypeSafe's own agent skill warns "agents aren't great at writing questions" and keeps questions and thresholds in one reviewed file. blakestone-x/jev-mcp keeps "all thresholds in one questions.py".
Rationale
Question quality is Jev's biggest accuracy lever. Free-form questions inside execute make this more important, not less, because agents will write them in loops.
Downsides
It needs a file format and loader, which costs lines. It isn't needed until a decision actually repeats; a skill containing example questions may be enough at first.

7. Later phase: a "second reader" for silent background runs

  • Idea 7
  • Later phase
  • Decisions RocketClaw makes itself
  • Confidence 35%
  • Complexity Low

Description

A background run sometimes ends by choosing to stay silent. In that case, the harness asks one yes/no question about the run's final output: "does this contain something the human asked to be told about?" If the answer is yes, it reuses the existing re-prompt loop once: "a second reader flagged this; decide again". The agent still owns what gets sent. System One never sends or suppresses anything, so the worst an injection can do is cause one extra re-prompt.

Axis
Decisions RocketClaw makes itself (later phase)
Basis
direct: bridge.go:990-993 already re-prompts until a decision is made. raw_run.go:224-233 exposes the empty-payload outcome. external: jevwire's rule that harness checks never emit "allow", applied here to delivery. Breast screening's rule that a second reader can only add a recall.
Rationale
Missed alerts from scheduled agents are quiet and costly. This check costs about 100 ms and can't make the system less safe. It reuses the first version's client unchanged.
Downsides
There is no evidence yet that the current mechanism misses anything. It adds a call to every silent run. It only makes sense after the first version ships.

Revision note. The first draft treated systemone as a top-level, strict-schema tool. Several ideas were shaped around problems execute doesn't have: a flattened question list, a host-added "none" option, a paths parameter, Go-side bands and batching. The checker's objection that Starlark calls run one at a time was also wrong, because map/gather fan out in parallel. This version is rebuilt on the confirmed execute behavior in codemode.go and fanout.go.
