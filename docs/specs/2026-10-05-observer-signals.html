RocketClaw: useful logs and a private diagnostic URL

The proposal: print useful measurements in the existing logs, and offer a private URL for deeper inspection. RocketClaw writes no diagnostic files: no saved profiles, trace files, or incident folders.

1. Print a small health report periodically

Start with one report per minute as a proposed cadence, then check its cost and log volume.

  • Memory: Go heap usage and allocation rate, plus time spent freeing unused memory.
  • Work: goroutine count and scheduling delays. These are clues, not proof that work is stuck or leaking.
  • Database connections: busy, idle, and total connections; count and duration of waits for a connection. This does not measure SQL query time.

Use runtime/metrics and the existing pool's sql.DB.Stats. Include the sampling interval and process-start identity; calculate rates from changes between samples. Runtime memory is not total operating-system memory usage. Routine reports stay at INFO, not WARN merely because a number is large.

2. Add measurements to the events we already log

  • Provider calls: provider, model, HTTP status, elapsed time, and attempt outcome—including successes. An unsuccessful retry attempt is not automatically a failed turn; HTTP return time is not full generation time.
  • Turns and tools: existing identities, observed operation, duration, and outcome. Distinguish first response item, first assistant text, human-question waits, and final delivery. Record parallel operations separately.
  • Queues and steers: accepted, persisted, handed to the agent, started, or explicitly removed; log queue age, due time, and the real blocker. Old work may be deliberately parked.
  • Delivery and background work: generated, text accepted, attachment failed, intentionally silent, stopped, or failed; include elapsed time. Preserve current acknowledgement and retry behavior.
  • Startup: actual revision when available, Go version, and process-start identity. A merged fix does not establish which binary is running.

Keep the existing text logs. Use consistent event names and key/value fields, existing identities, and milliseconds for durations. Do not print prompts, message bodies, tool arguments, credentials, or full request URLs.

event=delivery_finished turn_id=example-turn duration_ms=240 text_outcome=accepted attachment_outcome=failed

That example is invented. Extend existing events rather than add another system to track the same work.

3. Offer a private pprof URL

Yes—net/http/pprof is the Go facility for this. An opt-in listener such as http://127.0.0.1:6060/debug/pprof/ would let a trusted tool inspect memory allocation sites, goroutine stacks, or request a short CPU profile or execution trace.

Register only the needed handlers on a dedicated server. Keep it separate from the normal Web interface, which currently defaults to listening on all network interfaces. Bind diagnostics to loopback, leave it off unless enabled, and do not expose it through the public Web server.

RocketClaw sends diagnostic data straight back in the HTTP response; it does not save it to disk. A requesting tool may save its own copy. CPU profiles and ordinary execution traces record work after the request begins; they cannot reconstruct an incident that already ended. No automatic recording, disk-backed flight recorder, or always-on CPU/block/mutex profiling is proposed.

What the observation loop needs

Read the regular health reports as well as warnings and errors, and use event fields to follow the affected operation. Use the running build identity—not merge time—to determine whether a fix is present.

Live profiling is allowed. The observation loop may inspect memory and goroutine profiles and request short CPU profiles or execution traces through the private diagnostic URL. Its rules must explicitly permit those requests: CPU and trace recording temporarily turn on measurement and add overhead. This does not permit restarts, configuration changes, database writes, or diagnostic file writes by RocketClaw. Keep responses private and any local scratch copies under the observer repository's .tmp/.

Where the changes belong

cmd/rocketclaw owns the diagnostic listener and startup identity. The backend owns the periodic report and turn/queue/provider event fields. Slack and cron code report their own delivery and completion outcomes. Keep existing OpenTelemetry support; this proposal needs no new monitoring service or dependency.

Before shipping: test that the fields describe success, failure, intentional waits, and silence correctly; check that diagnostics cannot be reached through the public Web handler; measure sampling/profile overhead; and verify no diagnostic files are created.
