Ideation: Sticky voice mode

2026-11-03

Focus: keep the voice call alive while moving around the app; make the conversation behind voice mode stickier; let voice take you through the sessions that need you; turn the bottom-bar mic into the orb; show your spoken words and the session together on the right.

The short version. The call already lives outside the Voice page. The page hangs it up when you leave, because of one deliberate cleanup step. Removing that step and putting the orb in the bottom bar fixes the first complaint (ideas 1–2). The "not sticky" feeling comes mostly from a rule: a call is tied to one conversation for its whole life (idea 3). For navigation, OpenCode's voice in this repo already has working tools (list_sessions, open_session, send_message), so we can copy that design instead of inventing one (idea 4).

Grounding Context

Codebase Context

  • Why leaving ends the call. The call (mic, WebRTC, reconnect loop) lives in a module-level store in internal/rocketclaw/web/src/voice.ts (lines 34–35), so it survives the page going away. But the Voice page hangs up when it closes: ui.tsx:5418 says "The page owns its call: Reset and leaving the page hang it up." Calls started from a session's composer also hang up whenever the route changes (ui.tsx:5519). The original voice plan listed keeping the call alive across tabs as deferred work (docs/plans/2026-10-10-1146-feat-web-voice-mode-plan.md:110), and a browser test checks the current behaviour (voice-page.browser.test.ts:270).
  • How the conversation behind voice is chosen. Voice Settings keeps one row per person on the server, including the current voice conversation. Start reuses it, and Reset clears it. But a call's conversation is fixed when the call starts (frontend/rpc/voice.go:225). Hand-offs and spoken replies only ever use that conversation (voice.go:454, :612). A call started from a session's composer goes to that session, skips Voice Settings and replaces your Voice page call (ui.tsx:4691, voice.go:179-181). Every reconnect starts a new OpenAI call that only gets the last 40 messages (voice.go:194). The 60-minute limit ends the call outright instead of reconnecting (voice.ts:22, :31, :213).
  • What the voice model can do. It has no tools. Its instructions say "You cannot do any work yourself" (voice_wire.go:23), and it must hand every task to the conversation's agent. It is also told never to pass on an answer to a pending question (voice_wire.go:27). Nothing today lets the server or an agent move the browser to another page. The long-lived /api/Voice stream already sends events to the browser (answer, notice, reconnecting, reply, typed, ended; voice.ts:186-206), and in-app navigation is one function, navigate(path).
  • Bottom bar. The four centre buttons are New session, Search, Voice (mic) and Copy page link (ui.tsx:1910-1915). The mic only goes to /voice. The orb exists only on the Voice page (VoiceOrb, ui.tsx:5331).
  • Transcript vs timeline. The Voice page shows this call's captions, which live only in browser memory with no timestamps (voice.ts:9-12). The real session timeline is a separate component, shown only on session pages. Each hand-off is saved as a user message wrapping what was said, but it currently shows as raw text in a plain bubble (ui.tsx:3594).
  • Sessions that need you. These already exist as concepts: work state NEEDS_YOU, the search terms is:waiting and is:unread, the dashboard "Needs you" lane, and pending questions answered through AnswerQuestion.
  • In-repo prior art. OpenCode's voice in internal/rocketclaw/oc/packages/app/src/voice/ runs gpt-live-1 with a "responses" delegate that has browser-side tools: list_sessions, search_sessions, read_session, wait_for_session, create_session, send_message, open_session, interrupt_session (spec.ts, transport.ts:119-130).

Past learnings

  • Keeping views mounted in the background broke several things before (single composer ref, scroll lookups by id, URL-sync effects, 0×0 hidden views), and all traffic shares one HTTP/2 connection (docs/solutions/architecture-patterns/web-keep-alive-views-connection-budget.md). Takeaway: don't keep the Voice page mounted. Let a small shell control own the call.
  • SessionApp is at react-doctor's complexity limit. New UI branches go in small hooks or self-hiding components.
  • Tab state starts with a fake "main" space until the first load, so navigating straight after a space switch can land in the wrong space.
  • Remote OpenCode sessions must be driven through the /oc/{server}/api/ proxy, never through the mounted OpenCode view.

External context

  • ChatGPT Voice (Nov 2025) moved voice into the chat itself, with text you can scroll while talking. Its "Voice in Work and Codex" (Jul 2026) uses voice as a control room over several agents, with one live call at a time.
  • The car-messaging pattern (Android Auto, CarPlay) goes: read, dictate, read back, then "send / change / cancel". Users complain when the read-back is removed.
  • In LiveKit's and Pipecat's designs, the agent calls named commands in the page, such as navigate or set_input_value. Navigation stays inside the single-page app, so the call keeps running.
  • OpenAI realtime sessions are capped at 60 minutes. Continuity has to be owned and reloaded by the app.

1. The call belongs to the app; the mic turns the bottom bar into the orb

Call lifetime in the app shellConfidence 90%Complexity Low
Description

Delete the two cleanup steps that hang up on navigation: the Voice page's and the composer's. Then let the bottom bar read the call's state. When a call is live, the four centre buttons are replaced by the orb, and tapping the orb hangs up. Pressing the mic starts the call right where you are. The /voice page can stay as the place for settings (agent, voice, Reset) or move into a small menu on the orb. That is a smaller choice for later.

Axis
Call lifetime in the app shell
Basis

direct: ui.tsx:5418-5419: "The page owns its call: Reset and leaving the page hang it up." followed by an unmount effect that calls stopVoice(); ui.tsx:5519: the composer's call ends on any route change; voice.ts:34-35: the call store is module-level and survives page unmounts; ui.tsx:1910: the mic is only navigate("/voice").

external: persistent call or player surfaces: Spotify's player bar, Google Meet's picture-in-picture on tab switch, Slack huddles in their own window.

Rationale
This fixes your first complaint mostly by deleting code. It avoids the keep-alive traps from past work because no page has to stay mounted, only a small control that reads a store that already exists. Once the page cleanup is gone, the orb in the bottom bar is the only way left to hang up, so it is required, not optional.
Downsides
  • It reverses a deliberate earlier decision and flips an existing test (voice-page.browser.test.ts:270).
  • The tab-hidden-for-30-seconds rule (voice.ts:113) still ends calls when a phone screen locks. That needs its own decision if mobile matters.
  • The long-lived /api/Voice request now runs alongside every page. It carries only small events, since audio goes over WebRTC, so the risk to the shared connection looks low.
  • The bottom bar sits inside SessionApp, which is at its lint complexity limit. The orb has to be its own self-hiding component.

2. Calls outlive the 60-minute limit

Call lifetime in the app shellConfidence 85%Complexity Low
Description

Today a dropped connection reconnects automatically, but reaching OpenAI's time limit ends voice mode with "Call ended: time limit reached." Treat the time limit like a dropped connection: reconnect quietly on the same mic. Once the call survives navigation (idea 1), this is the next thing that will randomly end a long voice session.

Axis
Call lifetime in the app shell
Basis

direct: voice.ts:22 expired: "Call ended: time limit reached."; voice.ts:31 networkLosses = [lost, endings.lost, audioLost, timedOut] (no expired); voice.ts:213 returns without reconnecting when the error isn't in that list. The fact-checking agent confirmed all three.

external: OpenAI realtime sessions are capped at 60 minutes, so any all-day voice mode has to span several calls.

Rationale
This is the cheapest "stickiness" fix, about one line. It turns voice mode from "one OpenAI call" into "something that lasts as long as you want".
Downsides
A new call only gets the last 40 saved messages. Whatever was said after the last hand-off is lost at the rollover, same as on a reconnect today. Fixing that properly needs a way to save voice lines without starting an agent turn (see rejected idea B2).

3. One voice home, one movable focus

The voice home conversation and its rulesConfidence 70%Complexity Medium
Description

Split "who I'm talking to" from "what I'm looking at". Every call talks to your voice home, the conversation already stored in Voice Settings. The live call also carries a focus: the session you're working on right now, which moves when you navigate or when voice moves you. The composer mic stops starting a rival call that replaces your home call. It just means "keep the call going, focus here". Focus, and later your position in a walk-through, can live in Voice Settings, so a reconnect or a reload comes back to the same place.

Axis
The voice home conversation and its rules
Basis

direct: voice.go:225 sets the call's conversationID once at start; voice.go:612 watches only that conversation; ui.tsx:4691 startVoice(sessionId, speaker) starts a call on the composer's own session; voice.go:179-181 ends the older call as "replaced". CONCEPTS.md (Voice Session) says a call is "attached to one conversation".

reasoned: whether voice feels sticky currently depends on where you pressed the mic. Keeping home and focus separate makes the home stable and still lets you act on other sessions.

Rationale
You suspected "the implementation is right but the rules are wrong", and this is the rule at fault. Ideas 4–7 all need a call that can work on another session without dropping its home.
Downsides
  • It rewrites the Voice Session definition in CONCEPTS.md.
  • On the server, changing focus means re-checking that you can see the session, restarting the reply watcher, and resetting the "typed before the call" bookkeeping, which assumes one conversation (voice.go:500-518).
  • Remote OpenCode sessions can't be written to the same way local ones can.

4. Copy OpenCode's voice tools so voice can move the screen

Voice-driven navigation and triageConfidence 65%Complexity Medium–High
Description

Give the voice side a small set of session tools modelled on OpenCode's voice in this repo: list or search sessions, read one, open one (moves your screen), send a message, interrupt. The quick ones ("open", "next") run without waiting a full agent turn, so the walk-through feels instant. Real work still goes to the agent. If a tool has to run on the server instead, it moves your screen through one new event on the /api/Voice stream the browser already reads, which calls navigate(path).

Axis
Voice-driven navigation and triage
Basis

direct: internal/rocketclaw/oc/packages/app/src/voice/transport.ts:119-130 runs gpt-live-1 with delegation: { type: "responses", responses: { …, tools } }; spec.ts defines list_sessions, search_sessions, read_session, wait_for_session, create_session, send_message, open_session, interrupt_session. In contrast, RocketClaw's voice has no tools: voice_wire.go:23 "You cannot do any work yourself.", and the session sets only Delegation.Type = "client" (voice_wire.go:128-140). voice.ts:186-206 already handles typed server events on the voice stream.

external: LiveKit's concierge example has the agent call router.push in the page, and the call survives. Pipecat's ui-command set (navigate, set_input_value).

Rationale
"Send, let's go to the next" only works if "next" is fast. A full agent turn per step breaks the rhythm. Copying a design that already runs in this repo is cheaper and safer than inventing one, and it gives RocketClaw its first controlled way for voice to move the browser.
Downsides
  • Unknown: whether RocketClaw's ChatGPT sign-in route accepts the "responses" delegation with tools, or only "client". This needs a quick probe before committing.
  • It changes the voice model's core instruction.
  • A wrong "open" or "send" is now possible, so it needs ideas 5 and 6 for safety.
  • Moving the screen must wait for the first tab-state load, or it lands in the placeholder "main" space.

5. The "needs you" walk: fixed list, composer as the draft, "send, next"

Speaking into another sessionConfidence 60%Complexity Medium
Description

When you say "let's go through what needs me", take one snapshot of the sessions that need you, in the same order as the dashboard's "Needs you" lane, and walk through it with a cursor. At each session, voice gives a one-line summary. Whatever you dictate goes into that session's real composer as a visible draft, not straight into the session. "Send" submits the draft the normal way, "send, next" submits it and moves on, and "change it" or "cancel" edit or clear it. Because the list is fixed, sessions don't jump around or get repeated as you answer them.

Axis
Speaking into another session
Basis

direct: drafts already exist per session in the browser (ui.tsx:4674-4676), and the mounted composer has a ref (ui.tsx:1816). is:waiting, is:unread and the "Needs you" lane already exist. The voice prompt already asks for faithful wording (voice_wire.go:24).

external: car messaging (Android Auto, CarPlay): dictate, read back, then "send it / change it / cancel". Users complain when the read-back is removed. OpenAI notes its transcripts are not word-for-word.

reasoned: a live "needs you" list changes as you answer sessions, so "next" on a live list skips or repeats. A snapshot is the only stable meaning of "next".

Rationale
This is your example, step by step. The visible draft is the main protection against a misheard transcript being sent, and it reuses the composer's normal send instead of a hidden voice-only path.
Downsides
  • Drafts live only in the browser, so the server can't reach them. Filling the draft needs a browser-side tool (idea 4) or an event on the voice stream.
  • Deciding exactly when "send" is a command and when it's part of what you're dictating is the hard part. Reacting directly to words in the transcript risks running an action twice and misfires on late or inexact transcripts, so the voice model should decide, guided by its instructions.
  • Remote OpenCode sessions need the /oc/ proxy path.

6. Answer pending questions by voice, with a read-back

Speaking into another sessionConfidence 60%Complexity Medium
Description

Many sessions that "need you" are blocked on a question. Today voice reads the question out and then says "respond in the app", so a hands-free walk stops at nearly every stop. Allow a spoken answer for the focused session: voice repeats it in one sentence ("Answering 'Yes, migrate' on Deploy fix. OK?") and, once you confirm, submits it through the existing AnswerQuestion.

Axis
Speaking into another session
Basis

direct: voice_wire.go:27 "ask the person to respond in the app. Never hand off an answer to the agent's question."; voice.go:492 "I need your input. Please respond in the app."; CONCEPTS.md (Voice Hand-off): "A pending question is announced once and answered in the app, never by a hand-off."

external: read-back before acting (car messaging, pilot read-back). Practitioner advice on ChatGPT's agent voice: restate the interpretation in one sentence and approve each action separately.

Rationale
This is a clear case of a rule that made sense for a call stuck on one conversation but blocks the walk you described. A visible, read-back answer arguably still counts as "answered in the app".
Downsides
It changes a written safety rule. A wrong answer to a permission or form question can cost more than a wrong chat message, so some question types (permissions) might stay app-only.

7. One pane: the session's timeline with your spoken lines in between

The combined viewConfidence 65%Complexity Medium
Description

In voice mode, the right-hand pane shows the existing timeline of the focused session (or the voice home), with what you and the voice said placed between its messages in time order. When voice moves you to another session, a small divider shows it ("→ moved to Deploy fix"). Two things make this possible. First, give each caption a timestamp; today captions have none. Second, render saved hand-off messages as readable "you said / voice said" lines instead of the raw wrapper text they show as now.

Axis
The combined view
Basis

direct: voice.ts:9 VoiceCaption = { id; role; text; written? } has no time field, and captions "live only in memory" (voice.ts:10). ui.tsx:5493 shows only this call's captions on the Voice page, and the session is one click away ("Open conversation", ui.tsx:5488), which today hangs up. Hand-offs are saved with a <transcript_delta> of both sides' lines (voice.go:444-447) but render as a plain bubble (ui.tsx:3594).

external: ChatGPT Voice (Nov 2025) moved voice into the chat as scrollable text while you talk. OpenCode's in-repo session/timeline/voice-delegation.ts already parses hand-offs inside a timeline.

Rationale
Without it you're talking to a session you can't see. Reusing the existing timeline instead of building a new view keeps this mostly rendering work, and the saved part survives reloads.
Downsides
  • Saved hand-offs hold at most the last 4 KB of speech, and nothing after the last hand-off is saved. The live tail only shows on the device making the call.
  • Showing a second timeline in a side pane runs into the "one mounted timeline" assumptions from past work (scroll lookups by id, the single composer ref).
  • OpenAI can deliver your words after the voice has started replying, so time order is approximate.
