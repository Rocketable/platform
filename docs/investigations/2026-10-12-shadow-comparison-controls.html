Shadow comparison controls

2026-10-12 · Owner: Ulderico · Topic: shadow-comparison-controls · Grounded in the current Web UI

Focus: a better mobile entry point and less repeated shadow identity. These are design choices, not an implementation plan.

Context · Ranked ideas · Rejected ideas · References

Grounding Context

The supplied screenshots show a detached upper-right “Compare shadows” action below the session tabs. The comparison sheet already names the selected shadow in its tab strip, then repeats that name above each turn. The bottom composer has an agent picker, attachment control, Stash, Steer, and Send.

The source confirms this layout. Shadow tabs sit outside the mobile sheet’s scroller, so they can carry identity while rows carry turn numbers. Shadows are read-only comparison children, not choices for who answers the next message. Recorded turn pairing, parent-return links, and statuses must remain intact.

No directly applicable past design learning was found. An adjacent Web connection-budget learning cautions against introducing additional mounted transcript streams. General NN/G guidance favors scoped controls and a clearly selected tab; it does not prove which placement RocketClaw users prefer.

Topic Axes

Decomposition skipped — atomic subject. The placement alternatives are the deliverable.

Ranked Ideas

Recommended combination: keep shadow identity in the tabs only, and put a compact comparison control just above the composer, outside the sending controls. If avoiding another row matters more, use the session menu instead.

Approved refinement: reuse the source-filter row above the composer. Keep the grouped “sandboxed | canonical” toggles and a separate “Shadows” button; the button opens comparison rather than filtering messages or selecting an agent. Show only “Shadows” when source toggles are unnecessary, and let the row wrap on narrow screens. Keep parent context in the sheet heading, short shadow names in tabs, and turn numbers in shadow rows.

1. Name the shadow once

Description
Let the fixed selected tab identify the shadow. Change repeated row headings from “Turn 2 · main/concise” to “Turn 2.” Show short tab names such as “concise,” “skeptic,” and “structured” when their parent context is clear; retain full identities for accessibility and disambiguation.
Basis
direct: ui.tsx:2220 repeats the name; :2335–2337 already labels the tabs; :2362 keeps them outside the scroller.
Rationale
The selected shadow is a property of the view, not fresh information in every turn. Turn numbers still explain correspondence.
Downsides
Historical parent-agent segments can make shortened names ambiguous. Keep them distinguishable and preserve accessible context.
Confidence / Complexity
95% / Low. Confidence is a design judgment, not a measured user result.

Conceptual illustration: identity belongs to the view; correspondence belongs to the row.

2. A compact control above the composer

Description
Move “Compare shadows” to a small, left-aligned control immediately above and outside the message box. Keep it near the bottom agent picker without putting it inside that picker or squeezing it into the sending toolbar.
Basis
reasoned: the composer already occupies the lower interaction area and its authoring row is crowded (ui.tsx:3333–3348). An adjoining control improves reach while separating viewing from sending.
Rationale
Visible access without a detached top corner or confusion about which agent will answer.
Downsides
Uses some vertical space and requires the comparison state to be available outside its current transcript component.
Confidence / Complexity
80% / Medium. A visual trial on narrow screens would settle whether the additional row earns its space.

3. A left-aligned conversation control

Description
Keep comparison above the transcript, but make it a compact, left-aligned “Conversation · Compare shadows” row rather than an isolated action on the right.
Basis
direct: ui.tsx:2359 already has a desktop Conversation header while mobile uses a self-end button.
Rationale
Fixes the detached alignment with the smallest conceptual relocation and leaves the composer untouched.
Downsides
It remains near the top and adds permanent header prominence.
Confidence / Complexity
75% / Low.

4. Put comparison in the session menu

Description
Remove the standalone control and add “Compare shadows” to the active session’s existing ellipsis menu.
Basis
direct: ui.tsx:846–869 provides an active-tab scoped menu. It currently contains tab-management commands, so comparison would be a deliberate extension.
Rationale
The quietest transcript: no extra persistent control or row.
Downsides
One more tap, weaker discovery, and new session-specific wiring. The menu still sits near the top.
Confidence / Complexity
70% / Medium. Best if comparison is occasional.

5. A separate button beside the agent picker

Description
Place a distinct “Compare” button beside the composer’s agent picker. Never make shadows ordinary entries in the active-agent selector.
Basis
direct: ui.tsx:3335 establishes the picker’s lower location; CONCEPTS.md:141 says shadows are not ordinary agent-picker choices.
Rationale
A visible, nearby entry with no additional row.
Downsides
The supplied mobile toolbar is already full. It can crowd sending controls or imply comparison changes the active agent; this is not the preferred placement.
Confidence / Complexity
55% / Medium.

Rejection Summary
